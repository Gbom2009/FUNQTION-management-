# Architecture

## One repo, one hub, many apps

```
src/
  core/            shared by every app: data model, database, audit log, i18n (NL/EN),
                   session (Gijs/Coen + PIN), backup/merge, UI kit, brand styles
  hub/             the Funqtion Hub home screen + app registry (hub/apps.ts)
  apps/
    bookings/      App 01: Bookings & CRM
      domain/      pure logic with unit tests (pipeline, conflicts, reminders, templates, ics)
      pages/       screens
      components/  app-specific components
    <next-app>/    each future app gets its own folder
  settings/        suite-wide settings
  styles/          design tokens (from funqtion-site) + app styles
src-tauri/         native shell: Windows exe now, iOS/iPadOS later
.github/workflows  CI, Windows exe build, GitHub Pages deploy
```

### Adding a new app

1. Branch off `main` (e.g. `app/invoicing`).
2. Create `src/apps/<id>/` with its own `<Id>App.tsx` and routes.
3. Add its tables in `src/core/db.ts` as a new `this.version(n + 1).stores({...})` block. Existing tables are never redefined, so data from older versions upgrades automatically.
4. Put its types in `src/core/types.ts` (or a `types.ts` in the app folder) and reference shared records by id (`gigId`, `personId`, `organisationId`, `venueId`).
5. Write every change through `save()` / `patch()` from `src/core/repo.ts`, so the audit log covers it.
6. Register it in `src/hub/apps.ts` and add a route in `src/App.tsx`.
7. Merge to `main` → CI builds the web app and a new exe with all apps inside.

### How apps connect

The **gig** is the hub record. Future apps hang off `gigId`:

- Invoicing: copies `quote.lines` into an invoice, then sets the gig's `invoicedAt`/`paidAt` (shown in the pipeline).
- Contracts: generated from the accepted quote; signing moves the gig to *Confirmed* and creates the deposit invoice (see `docs/contracts/PLAN.md`).
- Gig-day planner: reads `setSlots`, `contacts`, `venue`, `musicWishes`.
- Gear: packing lists per `eventType`. `setupRequired` and `venue.houseSound` decide what to bring.
- Navigation: reads `venue` addresses for today's gigs, writes back trips (km) for accounting.

## Data and sync

- **Now:** local-first IndexedDB (Dexie). Works offline in the browser, in the exe and on iPhone. Sharing between devices is done with JSON export/import (newest `updatedAt` wins per record).
- **Later (self-host):** every record already has a UUID, `createdAt/By`, `updatedAt/By` and a soft-delete flag, and every change is in the `audit` table. A small sync server (e.g. PocketBase or Postgres on a cheap EU VPS) can replicate these tables without any reshaping. The backup format is also the migration format.

## Desktop and mobile shell

[Tauri 2](https://tauri.app) hosts `dist/` in a native window. It produces a small Windows exe (WebView2, already on Windows 10/11). The same project can build an iOS/iPadOS app with `tauri ios init && tauri ios build` on a Mac with Xcode. Distribution to your own iPhone needs an Apple Developer account (TestFlight). Until then the PWA (Safari → Add to Home Screen) gives a full-screen, offline-capable app.

## App 2: Quotes & Invoices (local mode)

- Lives in `src/apps/invoicing/`; adds the tables `invoices`, `payments` and `packages` (Dexie version 2) and extends `quotes` and `products`.
- Pure money logic is in `domain/money.ts` (totals per VAT rate, deposits, final invoices minus deposits, credit notes, cancellation scale, numbering) and is unit-tested.
- PDFs are built by `domain/pdfDoc.ts` (pdfmake document definitions, tested by rendering real PDFs in Node) and generated in the browser by `pdf.ts`. The fonts are embedded, so it works offline and in the exe. pdfmake is lazy-loaded, so it isn't part of the main bundle.
- Finalised invoices are immutable and carry a snapshot of the seller and client details. Corrections go through credit notes.
- Invoice numbers: a gapless series per member (`F<year>-G-0001`, `F<year>-C-0001`) so offline devices never collide.
- Payment reminders are generated by the same reminder engine as App 1 (tasks `dun1/2/3:<invoiceId>`), stop when paid, and can be paused per invoice.
- Business settings (address, KvK, IBAN, VAT mode, terms) live in the local `settings` record. The IBAN is never in source code.

## App 3: Money & Accounting (local mode)

- Lives in `src/apps/money/`; adds the Dexie version 3 tables `categories`, `expenses`, `receipts` (photo Blobs), `bankAccounts`, `bankLines`, `bankRules`, `trips`, `hours`, `assets`, `partnerEntries` and `vatPeriods`.
- **Reports are computed, never stored twice.** `domain/ledger.ts` derives P&L, profit per gig, the Gijs/Coen split, VAT boxes, depreciation and hours from the source records (invoices + payments from App 2, gigs from App 1, expenses, trips, assets).
- **Receipt OCR** runs on the device: Tesseract (Dutch model) in a web worker. Its assets are copied to `public/ocr` at build time by `scripts/copy-ocr.mjs`, lazy-loaded, and cached for offline use. `domain/receipt.ts` turns the text into amount/date/VAT/supplier guesses (robust to typical OCR errors such as "21%" → "214").
- **Bank import** (`domain/bank.ts`): ING, Rabobank, ABN AMRO TXT, bunq, Revolut personal and Business, CAMT.053 XML, plus a generic CSV fallback. Lines are de-duplicated by hash. `domain/match.ts` suggests invoice/expense matches and learns simple rules.
- **Backups v2** (`core/backup.ts`): a ZIP with `data.json` + receipt files, optionally AES-256-GCM encrypted with a passphrase (PBKDF2-SHA256). v1 JSON backups still import.
- **Accountant pack** (`reports.ts`): year report PDF + CSVs (invoices, receipts, expenses, trips, assets, partners, profit per gig, hours) + receipt images in one ZIP.

## App 4: Contracts (local mode)

- Lives in `src/apps/contracts/`; adds the Dexie version 4 tables `clauses`, `contractTemplates`, `riders`, `contracts`, `contractVersions`, `contractSignatures` and `contractEvents`.
- `domain/library.ts` holds the default clauses (NL/EN, business variants), one template per event type and two riders; seeded by `ensureContractLibrary()` (adds missing clause keys after updates).
- `domain/render.ts` is pure and tested: clause selection (template mode, client kind, outdoor/setup conditions, overrides), placeholders, the cancellation table with real dates, warnings, addendum diffs and the SHA-256 content hash over canonical JSON.
- **Frozen versions:** sending (or signing in person) freezes a `contractVersion` with a snapshot of everything the client sees (parties, gig, lines, clauses, rider, terms text + hash). `repo.save()` refuses to change a frozen snapshot or any signature field (`frozen_record`). Addenda are new versions with `prevHash` pointing to the signed version they amend.
- **Triggers** (`data.ts → finishIfComplete`): when both parties signed, the quote is accepted (with the extras chosen at signing), the gig is confirmed (with the conflict check) and a deposit invoice draft is created. App 2's `acceptQuote` asks `flowForGig()` first: *together* signs the sent contract, *after quote* creates the contract and leaves the gig at *quote sent*, *none* confirms as before.
- PDFs: `domain/pdfDoc.ts` (pdfmake, same paper style as App 2) with rider and terms annexes and a signature certificate page; the content hash is printed in every footer.
- Reminders: contract review, signature reminders (r1 after N days, r2 the day before the sign-by date), sign-by expired and "send deposit invoice" come from the shared reminder engine.

## Business rules (agreed)

- **VAT:** not registered → documents show no VAT and the note "Er wordt geen btw in rekening gebracht". Switch to KOR or VAT mode in Quotes & Invoices → Settings after registering.
- **Options ("optie"):** supported, with a default expiry of 14 days (configurable).
- **Contracts:** consumers get the softer cancellation scale, businesses the original one. The gig is booked when the agreement is signed (or, without an agreement, when the quote is accepted).
- **Profit split:** 50/50 by default; adjustable per period (fixed % or by lineup per gig).
- **Double bookings:** the same person can play two gigs on one day only if neither needs build-up (`setupRequired = false`) and there are at least 2 hours between them (configurable). Overlaps and blocked days are hard conflicts. Enquiries, options and sent quotes give soft warnings.
